# Android native development app

This isolated Compose app uses `tech.dongdongbh.mindwtr.nativeclient.dev` and its own private `mindwtr-native-dev.db`. It does not read or replace the React Native app. It has RN's tabs: **Inbox**, **Focus**, the quick-access tab (**Review**, **Contexts**, or **Projects**, as core's setting names), and **Menu**. Each list shows its first 50 rows, loads more in windows of at most 50, and calls the shared core contract to capture, complete, and edit tasks. The app has no sync, external intents, fixture seeding, or production upgrade path.

Every word on screen comes from core. At boot the app calls core's `setLanguage` with the React Native app's saved language (AsyncStorage `mindwtr-language`, read by the upgrade build's guard; none in the dev build) and the device locale, then reads one label map through `getStrings`. The keys are the ones mobile uses for the same controls (`Labels.kt`). Core fills in English for a key a language lacks; a key core does not know shows as the key and is logged once. Core has no key for "Refresh", "Load more", "Reload", or "Storage unavailable", so the app uses **Try again** (`common.retry`) for a failed read and for the editor's reload, **More** (`common.more`) for the next window, and shows a failed boot as its message alone.

The app looks like the React Native app, so an RN user recognizes it at once: RN's header, RN's bottom tab bar (Focus, Inbox, the center capture button, the quick-access slot, and Menu), RN's theme tokens (`Theme.kt`, the only file with colors), RN's lucide icons (`Icons.kt`), and RN's task row (`TaskRowView.kt`). A row shows core's meta line as core sent it (project or area dot, contexts, the due date in the user's format and core's urgency color, the checklist count; detail parts stay hidden, as in RN's lists and default Focus), core's priority strip, and core's TalkBack label. A swipe right reveals RN's labelled action button for the row's status (Done, Next, or Restore, from core's row meta): a tap runs it and a long-press opens RN's status menu, as in RN. TalkBack has the same action and Change Status as custom actions; there is no Done button, as in RN. The Inbox shows RN's status glyph and a project shows RN's status badge; a tap opens RN's status menu, which saves through core's `updateTask`. The header's left side is RN's area switcher (`AreaSwitcher.kt`): core's `getAreaFilter` label, and RN's sheet, where a tap sends core's `next` selection through `setAreaFilter`. A refused star shows core's text in RN's toast. The capture button opens RN's capture popup (`CaptureScreen.kt`) on core's quick capture contract (`native-host-contract-quick-capture.ts`): Add Task and Close, the field with core's live preview, the project or contexts chip with Focus and More, More's panel (the note, the Focus, due time, contexts, area, project and priority chips with RN's pickers, the syntax help, and Today, Tomorrow, Next week and Custom; the Custom date and due time pickers open on core's day and time), and RN's Add another switch (RN's Android switch: a raised thumb on a faint track; kept on the device under RN's key) with Save & edit and Save. Every chip and picker row sends the edit core put on it. Several lines ask core's question; Create tasks writes core's recovery snapshot under `files/snapshots` (as mobile does: a temporary file, a clash number, the 5 newest) and then one task per line in one write; the batch sends the name actually written, which is on disk with the request, so a retry sends the same snapshot and a stale one is replaced with a new snapshot and the same capture UUIDs. Each save's exact request (a capture UUID, one per line for several lines) is written to a synced file in the no-backup folder before the call; a failed one keeps its exact retry, and after process death it is sent again before anything else, so core writes it once. A refused date command shows core's notice and keeps the draft. The popup's draft (text, options, open picker, and chip edits not yet answered) survives rotation and process death; a request whose outcome was lost comes back even after a force-stop. Close discards the draft, as RN does. In portrait only More's panel scrolls, as in RN; in landscape everything under the header scrolls, so Save & edit and Save stay reachable above the keyboard. RN's microphone and Import .txt are not built. The theme is RN's choice as core resolves it: the synced `settings.theme`, else RN's device-local `@mindwtr_theme` (read by the upgrade build's guard), else the system's light or dark mode.

Each screen scrolls as one list, so landscape shows rows rather than fixed controls. The Inbox's first item is RN's **Process Inbox (N)** button (core's Inbox count, shown as 99+ above 99; TalkBack hears the exact count) with RN's "All areas" line under it; an empty Inbox has no button. Only the header, the tabs, and a failure message with its retry stay fixed.

The header's search button opens RN's global search on core's `searchTasks`: the field, Clear, RN's filter sheet (due date, location, contexts and tags, Include, status, scope, area, all core's words and choices), the active chips that clear a filter, core's truncation and hidden-matches lines, and the project and task results with core's highlights and date line. A task opens the editor over the search; a result core cannot open there goes to its list (Inbox, Focus, a project, or the Menu tab's Waiting, Someday, Reference, or History's Done or Archived). Clearing an active chip removes its filter value, so a second tap changes nothing. Mark Done is the lists' Done. Save Search saves through core's `saveSearch`: the submitted query, name and request UUID are kept with the screen before the call, the dialog stays locked to them until core answers, and after process death they are sent again before it unlocks. The saved-search screens are not built. An answer for an older query is dropped by core's echoed query.

**Process Inbox (N)** opens RN's step flow on core's session (`startInboxProcessing`, `getInboxProcessingStep`, `commitInboxProcessingStep`, `skipInboxProcessingTask`, `endInboxProcessing`): the progress header with Close, RN's guided/quick switch (kept on the device under RN's key `mindwtr:view:inboxProcessingMode:v1`) and Skip; the item's card with its editable title and note; then core's step, drawn from core's view, where every chip, date, and suggestion sends the exact edit core put on it, one at a time. Each answer (a choice, File it, Back, Skip) is a command with a request UUID: it is written to a synced file in the no-backup folder before the call, a failed one keeps its exact retry through rotation and a new screen. After process death the app lands on the Inbox, as RN does, and the owed answer is sent again in the background: core's session died with the process, so core refuses it without writing and its message shows. The record on disk goes only after core acknowledges or refuses the answer, so another death during that replay finds it again. Core refuses a new session while earlier writes are unsaved; its message shows. The failure message is drawn above the list and is a live region, so TalkBack always reaches it.

The **Menu** tab opens RN's More sheet on core's `getMoreMenu` (RN's `MoreNavigationSheet`): over the list and above the tab bar, a dimmed backdrop and a card with RN's handle, core's utilities (Trash, Board, History, Settings), core's saved searches, and core's six tiles, with RN's Ionicons in core's colors. A drag down, the backdrop, Back, the Menu tab again, another tab, or the capture button closes it. Waiting, Someday, Review, Reference, Contexts, History, Trash, and Projects open; Calendar, Board, Settings, and the saved searches keep RN's look but are drawn dimmed and disabled (TalkBack hears "disabled"), since those screens are not built yet.

The quick-access slot of the tab bar holds the view core's `quickAccessView` names, as in RN: **Review** (RN's default) or **Contexts** show that screen under the tab header, and Projects then moves to the More sheet, where its tile opens RN's Projects screen (a parked, archived, or searched project opens there too). Any other value shows Projects (Calendar is not built yet). The app reads the sheet at boot, so the tab bar draws the right tab from its first frame. A destination opens full screen over the tabs, as RN pushes it, under RN's stack header (Back and the title); Back returns to the tabs. Each list reads core's view in windows of 50 (**More** at the end) and each collection (people, parked projects, filter tokens and projects, saved searches) in core's windows of 100 through `getMenuViewCollection`, under the view's revision; a view that changed between windows is read again from its first window. Rows are RN's task row with RN's status glyph, and every list is read again on resume and after every command.

- **Waiting** (`getWaitingView`): core's stats, RN's person chips (All, each person, Clear), the parked projects (a tap opens the project; RN's swipe right, or TalkBack's action, runs core's `activateProject`), core's rows with their detail parts, and core's empty state.
- **Someday** (`getSomedayView`): core's stats with the filter summary chip (its X clears the filters) and RN's list menu (Filters, Sort, Group, Details, New section…), the parked projects, core's headings with their Add task, core's rows, and core's empty state. Sort, grouping, and details are RN's session choices. A row's status menu adds Move to section… (core's `getSomedayMoveDialog`, then `moveSomedayTasksToSection`); its toast has core's Undo (`undoSomedaySectionMove`). New section… (`createSomedaySection`, also from the move dialog, which then moves the tasks into it) and a heading's Add task (`addSomedaySectionTask`, with a capture UUID) keep their exact request in a synced file in the no-backup folder before the call; a failed one keeps its exact retry (the prompt's Retry), and after process death it is sent again before anything else, even after a force-stop; the record goes only after core answers.
- **Reference** (`getReferenceView`) and History's **Done** (`getDoneView`): RN's list menu in the header (Filters, then Sort and Group in RN's modals), the "Filters · N" button and the active chips with Clear, core's headings (a tap folds one, kept on the device under RN's `mindwtr:view:group-collapse:<list>:v1`), core's rows (an archived project's are read-only), and core's empty state with its Clear. Reference's sort is the stored task-list sort, a command (`setTaskListSort`); Done's grouping and sort are the device's, under RN's `mindwtr:view:done:v1`. Reference's filter sheet has the archived-projects switch.
- The filter sheet (RN's `TaskFilterSheet`) is core's filter view: the active filters, Search, the contexts-and-tags and projects pickers, time estimate, energy, and more filters (priority, location). Every chip and row sends the exact edit core put on it; only typed text (Search, Location) builds core's `setSearch` or `setLocation`, once typing pauses.
- **Contexts** (`getContextsView`, `runContextsAction`): the chip search, core's chips (All, No context, each context and tag, with core's counts), core's All/Any switch, core's rows, and core's empty state. A row swipes right to core's status action and left to RN's Delete (core's `trashTask`, whose toast has core's Undo); the status menu sends core's `setTaskStatus`. A long-press selects a row and opens RN's bulk bar: core's statuses, Add tag, Remove tag, Add context, Remove context (RN's token picker with core's tokens), and Delete (core's question first).
- **Trash** (`getTrashView`, `runTrashAction`): core's counts with Select and Clear Trash, core's retention hint, core's task and project items with core's type and deleted lines. A row swipes right to Restore (green, as in RN) and left to Delete permanently; Select opens the bulk bar (Select all, Restore, Delete permanently). Every delete forever, and Clear Trash, asks core's question first, and Clear Trash sends the revision its question showed, so core refuses it if Trash changed meanwhile.
- **Review** (`getReviewOverview` with its Due and All scope, `runReviewAction`): core's help line, RN's expansion button (core's cycle), Start Review (Daily or Weekly), and core's areas and projects that fold, with core's task rows; each row of the Due scope has Mark reviewed. A long-press selects a row: core's bulk actions (Move to, Mark reviewed, Add tag, Remove tag, Share through Android's share sheet, and Delete with core's question; Organize is drawn disabled). Back leaves selection first, as in RN.
- **Weekly Review** (`getWeeklyReview`, `getWeeklyReviewList`) and **Daily Review** (`getDailyReview`): full screen, as RN's review modals: the header with Close, core's step, progress and step rail (weekly), core's content for each step (Inbox with Process Inbox; stale tasks and projects; the calendar's task dates; Waiting and Someday with their not-yet-due group; contexts with their tasks; projects with Add task and the expanded project's rows; the summary; the Daily Review's Today, Focus with RN's stars, Inbox, and Waiting with Follow up today), and Back and Next (or Finish). Rows swipe and change status through core's `runReviewAction`, as on Review. The step is core's checkpoint, kept on the device under core's keys (`mindwtr:weeklyReview:currentStep`, `mindwtr:dailyReview:currentStep`), so Close keeps the place and Finish deletes it (the Weekly Review also stores core's `lastWeeklyReview`). A project's Add task sends core's `addProjectTask` with a request UUID that becomes the task's id; its exact request is in a synced file in the no-backup folder before the call and is sent again first after process death. The review's calendar step and the Daily Review's events show no external calendar events (the app reads no device calendar yet); Mind Sweep, the AI analysis, and the share card are drawn disabled.
- **History** (`getHistoryView`): core's Done and Archived tabs. **Archived** (`getArchiveView`, `runArchiveAction`): the Tasks and Projects chips, the search box with RN's list menu (Sort and Group, under RN's `mindwtr:view:archived:v1`), core's count with Select, and core's rows. A row swipes right to Restore (a task to Inbox, a project active again) and left to Delete, which asks core's question first; TalkBack has both as actions. Select opens RN's bulk bar (core's Select all, Restore to Inbox, Delete, whose toast has core's Undo).

The open sheet, screen, History tab, dialog, review step, selections, and RN's session choices survive rotation and process death. Every Menu write is a command with a request UUID (or a capture UUID) through the lists' command path, with its exact retry in the failure message's **Try again**. Not built yet, and listed as gaps: Archived's filter sheet and its completion-time picker (both need contract changes), the filter pickers' own search and the context/tag match mode (the filter view carries no edits for them), the token picker's search, Review's Organize sheet and its Review in 1 week (no contract yet), Mind Sweep, the review's AI analysis and share card, external calendar events, bulk selection on Waiting, Someday, Reference, and Done, RN's highlight of a task opened from search, RN's Settings › Manage for renaming, reordering, and deleting Someday sections, and RN's Menu sync dot.

From the repository root:

```sh
bun install --frozen-lockfile
node apps/android-native/scripts/build-bundle.mjs
cd apps/android-native/android
./gradlew :app:assembleDebug --offline
```

The build also regenerates `core-host.js` from current core source. Install only the resulting development APK (`android/app/build/outputs/apk/debug/app-debug.apk`) into the isolated development package. A clean install creates an app-private SQLite checkpoint before core schema setup. On later launches, the first checkpoint is retained. The checkpoint file and its directory entry are synced before task writes. Every core data load is checked against storage row counts, including the load during contract activation. A failed check shows only the failure message and offers no command. A capture that fails keeps its draft locked to its exact retry (the same capture UUID).

The checkpoint is a SQLite `VACUUM INTO` snapshot, so it includes committed WAL content. This development app has no other recoverable user data yet. It is not a tester build: its log is only in logcat, and it has no Settings › Diagnostics. A tester build needs that diagnostics screen, upgrade and recovery validation, and the remaining workflows before distribution.

The adapter rejects detected concurrent database writes, so the process owns exactly one core host (`ProcessCoreHost`). Activities and the Inbox `ViewModel` never close it; process death is the only shutdown. Screen state lives in the `ViewModel`, so rotation keeps an in-flight or failed save. A failed command's exact retry also stays with the process host until that retry succeeds, so a screen that is closed and reopened in the same process shows the failure and its retry again. The capture popup's draft survives process death on disk, and a capture whose outcome was lost is sent again with its capture UUID, so it is written once. `am force-stop` discards that saved screen state by Android design, but an owed capture on disk still comes back and is sent again.

Tapping a row opens the React Native task editor's Form tab. It reads core's `getTaskEditorModel` (the draft, the fields to show by section in the user's order, which sections start open, their filled counts, and every list a control picks from) and saves through core's `saveTaskDraft`; Kotlin holds no task rules. The header has RN's Close and Save; the title, then core's fields with RN's controls: status chips, the Destination picker (project or area), the section picker, the Someday section chips, the date rows (a date, or a date and a time from the clock button), context and tag fields with core's suggestions and quick chips (`getTaskEditorSuggestions`), priority, energy and time-estimate chips, the recurrence rule and "Repeat after completion", Skip reminders, assigned person, location, and notes. Every control's edit goes to core's `editTaskDraft`, one at a time, and the editor then shows the model core returns for the edited draft: its fields, sections and choices follow the draft as the user edits it. Dates show core's labels in the user's settings; a picked day keeps an existing time, the time picker starts at core's time for the field, and RN's quick date chips, Date only, the starts-after-due warning, the relative start (core moves it with the due date), the recurrence interval, days and ends, the repeat reminder intervals, and the custom time estimate all write core's values. Kotlin only turns the picker's day and time into `yyyy-MM-dd` and `HH:mm`, and core's picker start back into the picker. Typed text (title, notes, location) stays in the editor until Save. The checklist, attachments, and RN's custom monthly rule are shown read-only. Save sends only the changed draft fields, each with the value it was loaded with, and closes without a call when nothing changed; typed context, tag, and person text waits until core has said which draft value it stands for. If another writer changed a field you edited, core refuses the save, the draft stays, and **Try again** takes the stored value of each changed field while keeping your other edits. A failed or timed-out save locks the draft to its exact retry, like a failed capture. Leaving with unsaved edits asks Discard / Save / Cancel, as the mobile editor does. Typed text core has not resolved counts as an unsaved edit. Choosing Waiting first asks who or what it waits for, as RN does. The draft (its edits with the values they were loaded with, and the typed text) is kept in a synced file in the app's no-backup folder; saved instance state holds only that file's key. After process death core's model is read again and the draft goes on top, so a save still detects another writer's change. A save's exact request is written to that file before the call; if the process dies before core answers, the relaunch sends it again before the draft unlocks, and core writes nothing twice.

The **Focus** tab shows core's `getFocus` reply as it is: core's sections in core's order, with core's titles and totals, and each section's first 50 rows. **More** reads that section's next window through `getFocusSectionWindow`. Kotlin holds no Focus rules: it never sorts, filters, or groups rows, and it never reads a date. It uses only two row flags from core. A **Later today** heading goes before the first row core marks `laterToday`, and an Upcoming row shows core's `revealLabel` text as it is. Above the sections is core's date line (`dateLabel`) with RN's Focus only / Expand sections button. A section core counts as empty is not drawn, and "Projects to review" follows the task sections when core lists any. A tap on a section title folds it; which sections are open is kept on the device under RN's key `mindwtr:view:focus:v1`, in RN's JSON. Each row has RN's star (core's `setTaskFocus`; drawn disabled with core's `focusBlockedLabel` where the section sends one, as on Upcoming); a review-due row also has RN's status badge. Focus changes with the clock, so the app reads it again from the first row when the screen resumes, once a minute while Focus is on screen, and after every command. A refresh keeps each section as deep as More left it. If Focus changed before a More (core answers `STALE_REVISION`), the app reads Focus again from the first row; this is not an error. Complete (core's **Done** label) and the editor work from Focus exactly as from the Inbox, with the same exact-retry lock after a failure. Save and Cancel return to the tab the editor was opened from. The selected tab survives rotation and process death. A failed command's retry keeps its tab and rows, so a new screen reopens on Focus if the failure happened there.

The **Projects** tab starts with RN's **Add new project…** field: + (or Done on the keyboard) runs core's `createProject` with the area chosen on RN's area chips (by default the one area the filter selects). The draft, its area, and its request UUID survive process death; a failed create keeps its exact retry, and after process death the draft comes back but nothing is sent until + is tapped again. Then core's `getProjects` groups as they come: Active, then Someday / Waiting and Closed, which start closed and open on a tap, as on mobile. Each area header is core's area name (**No area** without one) with RN's colored dot and chevron, and folds its projects. Open groups and folded areas are kept on the device under RN's key `mindwtr:view:projects:v1`. A row shows the title, core's next action, its "No next action" warning, or core's status line, then core's active task count and RN's star (core's `setProjectFocus`, dimmed and disabled when five projects are starred). Tapping a project opens core's `getProjectDetail`: section markers and task rows in core's order, core's sequence cue under a row, and **More** for the next window. If the project changed between windows (core answers `STALE_REVISION`), the app reads it again from the first item. A row opens the editor and swipes to Done, except in an archived (read-only) project, whose rows have no swipe and a disabled status badge, as mobile does. Back returns to the list. The open project survives rotation and process death, and it is read again on every resume and after every command. A failed Done in a project keeps its exact retry, as on the other lists.

While a command's retry is owed, every screen's failure message offers **Try again**, which sends that exact request again, so a command started where its control is gone (a status change from the menu on Focus) stays retryable.

Reads the app starts on its own (on resume, each minute, and after every command) never disable a control, so a tap during one still runs; the engine thread queues both. Each read takes a number, and a command outdates every read that started before it, so an older result is never shown over a newer one.

Debug builds read three fault properties before each create, complete, or update command, and one language property at boot; release builds never read them:

- `debug.mindwtr.native.fail_commit=1` makes every SQLite `COMMIT` fail.
- `debug.mindwtr.native.delay_before_ms=<ms>` holds the command before it runs.
- `debug.mindwtr.native.delay_after_ms=<ms>` holds the acknowledgment after the commit.
- `debug.mindwtr.native.language=<code>` replaces the saved language (for example `zh`) for the next process, so a check never changes the phone's language.

`node apps/android-native/scripts/check-lifecycle-device.mjs <adb-serial>` uses these to check capture through rotation, process death, force-stop, and a failed commit that survives rotation, Back, and a new screen. It refuses any APK whose package is not the development package (checked with `aapt2`). It installs with `install -r`, keeps existing development data, and asserts on task titles unique to each run. Leave the device on its home screen first; the script stops (exit 3) rather than type into another app. It needs host `sqlite3`.

`node apps/android-native/scripts/check-editor-device.mjs <adb-serial>` checks the editor the same way: a save that changes the title, the due date, and a typed context; clearing a due date; a draft kept through rotation and through process death; a failed commit that keeps its exact retry through rotation, Back, and a new screen; a context chosen from core's suggestions and a due date with a time, in one save; and status Reference (core clears the due date) with a project from the Destination picker. It has the same install, safety, and exit-code rules as the lifecycle check.

`node apps/android-native/scripts/check-focus-device.mjs <adb-serial>` checks Focus the same way: two captured tasks set to Next appear under **Next actions**; a due date of today, picked on the day the picker marks as today, moves one under **Today**; Done from Focus stores `done` once; rotation and process death keep the Focus tab; the star moves a row under Today's Focus and back, stored once each; a failed Done keeps its exact retry through rotation, Back, and a new screen; and, on a fresh process after the relaunch, More adds rows to a section with more than 50 rows (the step is skipped when the development data has no such section). It has the same install, safety, and exit-code rules, and it leaves the app on its Inbox tab.

It reads the Projects tab, so its preparation also sets RN's quick-access view to Projects through core (RN's default, Review, takes the slot). It needs host `sqlite3` and `bun`.

The device checks type digits through the phone's own keyboard and never change its settings. Before launching and before any typing they read the current keyboard layout from `dumpsys input_method`; unless it is English (a Chinese Pinyin layout holds or reorders typed digits), or when the layout cannot be read, they stop with exit 3 and ask you to switch it with the globe key. `MINDWTR_KEYBOARD_OK=1` skips this after you have checked the keyboard yourself.

The lifecycle check proves each owed capture was sent again exactly once (one task carries the capture UUID it read from the no-backup file before the relaunch), scrolls the landscape popup to Save, and checks that the landscape Inbox shows at least three full task rows once its Process Inbox button scrolls away. The checks read the Inbox count from that button's spoken label (0 for RN's empty Inbox). All device checks clear the language property first, so they expect the phone's language to resolve to English.

Rotation and process death are validated only for this development identity, not for a production identity.

The `upgradetest` build type (`./gradlew :app:assembleUpgradetest`) is for the upgrade harness only. It installs as the throwaway package `tech.dongdongbh.mindwtr.upgradetest` over a real RN v1.3.2 build and opens the RN database, `files/SQLite/mindwtr.db`. Before anything opens that file, a guard refuses to start when the database is missing while other RN state exists and RN AsyncStorage (`databases/RKStorage`) holds no JSON backup, when that backup is over 64 MB, or when either file cannot be read or the database fails `quick_check`. The guard reads byte copies in the cache folder, never the files themselves. On a refusal the app shows the refusal message and changes no file. Otherwise the JS host imports the backup as RN's next launch would (core `planLegacyJsonImport`: the `mindwtr-data:json-ahead-of-sqlite` marker, the one-time reconcile, or an empty or missing database). After the import is saved and read back with every field equal, the guard copies `RKStorage` once to `files/SQLite/RKStorage.prewrite/`, then deletes the marker and/or sets the reconcile flag in one transaction. If either step fails, the app shows the failure message and makes no native write; the next boot retries only the `RKStorage` change. `node scripts/build-upgrade-harness.mjs` builds and signs the three harness APKs; `node scripts/check-upgrade-device.mjs <adb-serial>` runs the upgrade, JSON-backup import, damaged-database, missing-database and RN recovery scenarios on a phone. See the Harness section of `docs/development/native-android-upgrade-inventory.md`. `node scripts/capture-parity-screens.mjs <adb-serial>` uses the same harness APKs to shoot Inbox, Focus, Projects, one task's editor, global search, Process Inbox's first step, the capture popup, the Menu tab (the More sheet, Waiting, Someday, History's Done, Contexts, Trash, and Review), and the Weekly Review's first step in light and dark mode, first in RN 154 and then in the native build, on one fixture database built through core, and writes side-by-side PNGs (RN left) to `/home/dd/.mindwtr-harness/parity/<timestamp>/`.
