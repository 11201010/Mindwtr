# Android native development app

This isolated Compose app uses `tech.dongdongbh.mindwtr.nativeclient.dev` and its own private `mindwtr-native-dev.db`. It does not read or replace the React Native app. It has three tabs, **Inbox**, **Focus**, and **Projects**. Each list shows its first 50 rows, loads more in windows of at most 50, and calls the shared core contract to capture, complete, and edit tasks. The app has no sync, external intents, fixture seeding, or production upgrade path.

Every word on screen comes from core. At boot the app calls core's `setLanguage` with the React Native app's saved language (AsyncStorage `mindwtr-language`, read by the upgrade build's guard; none in the dev build) and the device locale, then reads one label map through `getStrings`. The keys are the ones mobile uses for the same controls (`Labels.kt`). Core fills in English for a key a language lacks; a key core does not know shows as the key and is logged once. Core has no key for "Refresh", "Load more", "Reload", or "Storage unavailable", so the app uses **Try again** (`common.retry`) for a failed read and for the editor's reload, **More** (`common.more`) for the next window, and shows a failed boot as its message alone.

The app looks like the React Native app, so an RN user recognizes it at once: RN's header, RN's bottom tab bar (Focus, Inbox, the center capture button, Projects in the quick-access slot, and an empty slot where Menu goes), RN's theme tokens (`Theme.kt`, the only file with colors), RN's lucide icons (`Icons.kt`), and RN's task row. The capture button opens RN's quick capture sheet, which uses the same capture path and exact retry as before. The theme is RN's choice as core resolves it: the synced `settings.theme`, else RN's device-local `@mindwtr_theme` (read by the upgrade build's guard), else the system's light or dark mode.

Each screen scrolls as one list, so landscape shows rows rather than fixed controls. The Inbox count line is the list's first item; only the header, the tabs, and a failure message with its retry stay fixed. The failure message is drawn above the list and is a live region, so TalkBack always reaches it.

From the repository root:

```sh
bun install --frozen-lockfile
node apps/android-native/scripts/build-bundle.mjs
cd apps/android-native/android
./gradlew :app:assembleDebug --offline
```

The build also regenerates `core-host.js` from current core source. Install only the resulting development APK (`android/app/build/outputs/apk/debug/app-debug.apk`) into the isolated development package. A clean install creates an app-private SQLite checkpoint before core schema setup. On later launches, the first checkpoint is retained. The checkpoint file and its directory entry are synced before task writes. Every core data load is checked against storage row counts, including the load during contract activation. A failed check shows only the failure message and offers no command. Capture drafts stay visible after save failure and reuse their UUID for an unchanged retry; editing the draft starts a new capture.

The checkpoint is a SQLite `VACUUM INTO` snapshot, so it includes committed WAL content. This development app has no other recoverable user data yet. It is not a tester build: its log is only in logcat, and it has no Settings › Diagnostics. A tester build needs that diagnostics screen, upgrade and recovery validation, and the remaining workflows before distribution.

The adapter rejects detected concurrent database writes, so the process owns exactly one core host (`ProcessCoreHost`). Activities and the Inbox `ViewModel` never close it; process death is the only shutdown. Screen state lives in the `ViewModel`, so rotation keeps an in-flight or failed save. A failed command's exact retry also stays with the process host until that retry succeeds, so a screen that is closed and reopened in the same process shows the failure and its retry again. Only the capture draft and its UUID survive process death, so an unchanged restored draft retries without a duplicate. `am force-stop` discards that saved screen state by Android design.

Tapping an Inbox row opens a task editor for title, notes, status, priority, project, start date, and due date. It reads through core's `getTaskEditor` and saves through `updateTask`; Kotlin holds no task rules. Save sends only the changed fields, each with the value it was loaded with, and closes without a call when nothing changed. Dates are picked as `YYYY-MM-DD` or cleared; a stored date with a time is shown as stored (timed editing is not built yet). If another writer changed a field you edited, core refuses the save, the draft stays, and **Reload** takes the stored value of each changed field while keeping your other edits. An invalid combination shows core's message and writes nothing. A failed or timed-out save locks the draft to its exact retry, like a failed capture. Leaving with unsaved edits asks Discard / Save / Cancel, as the mobile editor does. The draft and the values it was loaded with survive rotation and process death, so a save after a restart still detects another writer's change.

The **Focus** tab shows core's `getFocus` reply as it is: core's sections in core's order, with core's titles and totals, and each section's first 50 rows. **More** reads that section's next window through `getFocusSectionWindow`. Kotlin holds no Focus rules: it never sorts, filters, or groups rows, and it never reads a date. It uses only two row flags from core. A **Later today** heading goes before the first row core marks `laterToday`, and an Upcoming row shows core's `revealDate` text as it is. Section titles stay pinned while their rows scroll. Focus changes with the clock, so the app reads it again from the first row when the screen resumes, once a minute while Focus is on screen, and after every command. A refresh keeps each section as deep as More left it. If Focus changed before a More (core answers `STALE_REVISION`), the app reads Focus again from the first row; this is not an error. Complete (core's **Done** label) and the editor work from Focus exactly as from the Inbox, with the same exact-retry lock after a failure. Save and Cancel return to the tab the editor was opened from. The selected tab survives rotation and process death. A failed command's retry keeps its tab and rows, so a new screen reopens on Focus if the failure happened there.

The **Projects** tab shows core's `getProjects` groups as they come: Active, then Someday / Waiting and Closed, which start closed and open on a tap, as on mobile. Each area header is core's area name (**No area** without one). A row shows the title, core's next action or its "No next action" warning, a star when starred, and core's active task count. Tapping a project opens core's `getProjectDetail`: section markers and task rows in core's order, core's sequence cue under a row, and **More** for the next window. If the project changed between windows (core answers `STALE_REVISION`), the app reads it again from the first item. A row opens the editor and has Done, except in an archived (read-only) project, which shows its rows without Done, as mobile does. Back returns to the list. The open project survives rotation and process death, and it is read again on every resume and after every command. A failed Done in a project keeps its exact retry, as on the other lists.

Reads the app starts on its own (on resume, each minute, and after every command) never disable a control, so a tap during one still runs; the engine thread queues both. Each read takes a number, and a command outdates every read that started before it, so an older result is never shown over a newer one.

Debug builds read three fault properties before each create, complete, or update command, and one language property at boot; release builds never read them:

- `debug.mindwtr.native.fail_commit=1` makes every SQLite `COMMIT` fail.
- `debug.mindwtr.native.delay_before_ms=<ms>` holds the command before it runs.
- `debug.mindwtr.native.delay_after_ms=<ms>` holds the acknowledgment after the commit.
- `debug.mindwtr.native.language=<code>` replaces the saved language (for example `zh`) for the next process, so a check never changes the phone's language.

`node apps/android-native/scripts/check-lifecycle-device.mjs <adb-serial>` uses these to check capture through rotation, process death, force-stop, and a failed commit that survives rotation, Back, and a new screen. It refuses any APK whose package is not the development package (checked with `aapt2`). It installs with `install -r`, keeps existing development data, and asserts on task titles unique to each run. Leave the device on its home screen first; the script stops (exit 3) rather than type into another app. It needs host `sqlite3`.

`node apps/android-native/scripts/check-editor-device.mjs <adb-serial>` checks the editor the same way: a save that changes title, priority, and due date; a draft kept through rotation and through process death; a failed commit that keeps its exact retry through rotation, Back, and a new screen; clearing a due date; and core's refusal of status `reference` with a priority. It has the same install, safety, and exit-code rules as the lifecycle check.

`node apps/android-native/scripts/check-focus-device.mjs <adb-serial>` checks Focus the same way: two captured tasks set to Next appear under **Next actions**; a due date of today, picked on the day the picker marks as today, moves one under **Today**; Done from Focus stores `done` once; rotation and process death keep the Focus tab; a failed Done keeps its exact retry through rotation, Back, and a new screen; and More adds rows to a section with more than 50 rows (the step is skipped when the development data has no such section). It has the same install, safety, and exit-code rules, and it leaves the app on its Inbox tab.

`node apps/android-native/scripts/check-projects-device.mjs <adb-serial> [--prune-old]` checks the Projects tab. The app cannot create projects, so the script stops the app and, through core's own store on a host copy of the database, prepares one fixture found by stable titles: a sequential project with two sections, an archived project, and a project with 55 tasks. The first run injects it; later runs reuse it and only set its sequential tasks back to Next, so the development data does not grow. `--prune-old` also deletes, through core, the per-run projects and areas that earlier versions of this check injected. It then compares the screen with core's own replies on fresh copies: counts and next actions on the list, section markers, rows, and sequence cues in a project, Done stored once, the editor from a project, rotation and process death keeping the open project, a failed Done keeping its exact retry through rotation, Back, and a new screen, Back to the list, the read-only archived project, and More. It needs host `sqlite3` and `bun`.

`node apps/android-native/scripts/check-language-device.mjs <adb-serial>` checks that the tabs, the capture button, and the Inbox count line show core's English, then core's Chinese with `debug.mindwtr.native.language=zh` in a fresh process, then English again.

The lifecycle check also checks that the landscape Inbox shows at least three full task rows once its count line scrolls away. All device checks clear the language property first, so they expect the phone's language to resolve to English.

Rotation and process death are validated only for this development identity, not for a production identity.

The `upgradetest` build type (`./gradlew :app:assembleUpgradetest`) is for the upgrade harness only. It installs as the throwaway package `tech.dongdongbh.mindwtr.upgradetest` over a real RN v1.3.2 build and opens the RN database, `files/SQLite/mindwtr.db`. Before anything opens that file, a guard refuses to start when the database is missing while other RN state exists and RN AsyncStorage (`databases/RKStorage`) holds no JSON backup, when that backup is over 64 MB, or when either file cannot be read or the database fails `quick_check`. The guard reads byte copies in the cache folder, never the files themselves. On a refusal the app shows the refusal message and changes no file. Otherwise the JS host imports the backup as RN's next launch would (core `planLegacyJsonImport`: the `mindwtr-data:json-ahead-of-sqlite` marker, the one-time reconcile, or an empty or missing database). After the import is saved and read back with every field equal, the guard copies `RKStorage` once to `files/SQLite/RKStorage.prewrite/`, then deletes the marker and/or sets the reconcile flag in one transaction. If either step fails, the app shows the failure message and makes no native write; the next boot retries only the `RKStorage` change. `node scripts/build-upgrade-harness.mjs` builds and signs the three harness APKs; `node scripts/check-upgrade-device.mjs <adb-serial>` runs the upgrade, JSON-backup import, damaged-database, missing-database and RN recovery scenarios on a phone. See the Harness section of `docs/development/native-android-upgrade-inventory.md`. `node scripts/capture-parity-screens.mjs <adb-serial>` uses the same harness APKs to shoot Inbox, Focus, and Projects in light and dark mode, first in RN 154 and then in the native build, on one fixture database built through core, and writes side-by-side PNGs (RN left) to `/home/dd/.mindwtr-harness/parity/<timestamp>/`.
