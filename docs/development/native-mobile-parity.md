# Native mobile workflow parity and release evidence

Baseline: **v1.3.2**, commit **ee82a9e3e9a1d4e0c406f5ffff80e768a1f1f812**, frozen 2026-09-22. Execution order and release policy: [migration roadmap](native-mobile-migration.md).

This is the initial source-grounded inventory, not a declaration of native parity. Before closing each row, inspect the baseline behavior and split it if independently supported variants need separate evidence. Omitted baseline capabilities remain in scope. Platform availability follows released behavior, not an assumption that both platforms offer every integration.

## Current iOS status — 2026-10-02

The native iOS app is a development app with substantial local workflow coverage, not a release-ready replacement. The foundation, task browsing/capture, much of the editor, projects, organization, reviews, calendar/board views and selected Settings flows have implementation and focused evidence below. Roughly halfway through visible workflows is a planning estimate, not a measured completion percentage; release readiness is less advanced.

Recent accepted slices include task-to-project promotion, Focus start-date inclusion, Auto-archive, Task Editor layout controls and Reset, RN-shared task opening modes, single Task/Project Trash restore, Project Delete/Undo, Duplicate, Complete/Reactivate and Cancel. Remaining work includes bulk/recovery actions, remaining Settings, file attachments/import/export/backup, sync and encryption, reminders/external calendars, widgets/Siri/Watch/audio/AI, full accessibility/iPad/performance coverage, and signed RN-to-native upgrades with credentials and mixed-client sync. Passing an individual slice does not close its entire workflow row or any release gate.

## How to record progress

Per-platform progression: **N** not implemented/integrated → **I** implemented → **A** automatically checked → **D** device checked → **R** release ready. Stages accumulate evidence. For visual/accessibility checks, record the appropriate human check and why automation is not applicable rather than inventing a test.

**P** means related Android pilot code was reported in ADR 0029; it is not acceptance of the complete workflow. **—** means no native evidence recorded here. **N/A** requires baseline platform unavailability, not an unimplemented native feature. Applicable rows block release until verified or an intentional replacement is explicitly accepted.

RN behavior and regression history are required inputs to each migration slice. Before acceptance, inspect the actual RN screen/controller, its shared policy, relevant tests and fix history; record which prior failure cases have native evidence and which remain open. The frozen baseline defines the inventory, not a reason to omit later RN fixes informed by user feedback. Reusing shared policy alone does not establish interaction or recovery parity, and unfinished native behavior is not an approved difference.

Each evidence link identifies commit, artifact/core hashes, device/OS or test environment, fixture/provider/channel, date, exact check and outcome. Keep sensitive contents/credentials out of reports. Record automated and hands-on results separately; injected taps, simulator results, and existing RN tests are not physical-device native verification. Link failures to an issue, and accepted differences to a dated maintainer decision.
